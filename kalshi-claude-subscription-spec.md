# Kalshi Research and Trading System

Specification for Claude Code using an existing Claude subscription

Version: 2.0 — November 22, 2026
Owner: Andrew
Status: Development specification; live trading is not authorized.
Primary constraint: No separately billed Claude API or other paid model API usage.

This document replaces the earlier API-based proposal. It specifies a small personal application that collects Kalshi data, uses Claude Code for bounded research, evaluates independently implemented strategies, and eventually executes trades within explicitly approved limits. The first deliverable is a working recorder and paper workflow. Profitability is an unproven hypothesis to evaluate, not a promised feature.

The requirements below are proposed engineering decisions unless explicitly identified as a verified external fact. Dollar values in examples are paper-test fixtures, not Andrew’s selected bankroll or permission to risk money.

## 1. Decisions and boundaries

### 1.1 Required outcome

Build a maintainable personal system that can:

1. Record contemporaneous market information and external evidence.
2. Use Andrew’s own Claude Code subscription for research and development.
3. Produce reproducible research records with sources, timestamps, uncertainties, and abstentions.
4. Evaluate a small, approved market universe using a versioned deterministic strategy.
5. Paper-trade against production observations with conservative fill assumptions.
6. Measure forecast quality, simulated results, and operating costs honestly.
7. Test order mechanics with Kalshi demo credentials separately from strategy evaluation.
8. Support a later, explicitly authorized live pilot, with execution isolated from Claude.

Automatic live execution remains the eventual objective. Routine orders generated by an approved deterministic strategy need not require individual manual approval. Claude’s new discretionary buy/sell opinions, invented probabilities, and proposed strategy changes do not become live orders automatically.

## 2. Current external facts that affect the design

Reverify these facts before implementing the corresponding integration. Record retrieval date, installed CLI version, API-contract version or content hash, and relevant source URLs in docs/INTEGRATION_NOTES.md.

### 2.1 Claude subscription and scheduling

Anthropic currently documents that the Agent SDK and claude -p can draw from subscription limits when signed in with a Claude plan. Official cloud scheduled tasks also consume subscription usage. Neither capability makes usage unlimited. [S1, S2, S5]

The current CLI has credential precedence and fallback behavior: a non-interactive run can use an API key if one is present, and an expired subscription login can expose another configured credential. The current --bare mode does not use subscription OAuth; documentation says its default behavior may change. The research launcher must therefore verify the exact installed version and effective authentication rather than assuming that -p always means subscription billing. [S2, S3]

Usage credits can continue work at additional consumption-based charges after included usage is exhausted. The required setting for this project is disabled. [S4]

### 2.2 Research and financial decisions

Anthropic’s current usage policy requires meaningful qualified human review for personalized high-risk investment recommendations before implementation. It separately describes internal research and fixed-algorithm uses that are not the ultimate high-risk recommendation. [S6]

Design interpretation: Keep Claude’s discretionary opinions in research and paper evaluation. Automatic live orders must arise from independently computed, approved strategy rules. A risk cap alone does not establish that an unreviewed model recommendation is acceptable. If a future feature would turn Claude’s current subjective recommendation directly into a trade, review that workflow against the applicable policy before adding it. This specification is not a legal determination about every possible Kalshi use.

### 2.3 Kalshi integration

Kalshi’s official MCP supports research and selected account reads, but does not place or cancel orders. Use it only as an optional research interface. Execution uses the official trading API. [S7]

Current event order writes use /trade-api/v2/portfolio/events/orders and a single-book bid/ask representation with fixed-point fields. Legacy order-write examples can be obsolete. The adapter must use the then-current official schema, price grids, authentication, and error handling. [S8]

Kalshi documents that client-order-ID duplicate protection is limited to open orders. A retry after an order has filled or terminated can therefore repeat a trade. Local durable intent tracking and reconciliation are mandatory. [S9]

### 2.4 Runtime

Prefer .NET 10 LTS on a current supported patch. The earlier .NET 9 suggestion is obsolete for a new deployment: Microsoft’s current lifecycle table marks .NET 8 and 9 out of support. Verify the installed SDK and supported target before scaffolding. [S10]

## 3. Smallest useful architecture

### 3.1 Components

Use one .NET solution with clear modules, a single execution writer, and SQLite. Do not introduce microservices merely to express boundaries in a diagram.

Enforce one active executor for each account/mode through an exclusive lock in a protected, fixed runtime location. A second instance must refuse execution even if configured with another database path. Initial deployment supports one executor host; operating several hosts would require a separately designed fencing mechanism and is out of scope.

|Component             |Responsibility                                                                        |Must not do                                            |
|----------------------|--------------------------------------------------------------------------------------|-------------------------------------------------------|
|Market recorder       |Discover allowed series, collect rules and books, persist timestamps and raw responses|Infer missing prices or create live orders             |
|Evidence collector    |Retrieve approved external data and retain its publication/observation time           |Treat a later revision as if it were available earlier |
|Research export/import|Export bounded packets; validate Claude research JSON; store provenance               |Execute commands or promote rules contained in research|
|Strategy evaluator    |Compute signals and probabilities from frozen model versions and validated inputs     |Accept Claude confidence as calibrated probability     |
|Risk engine           |Authorize and reserve new risk atomically                                             |Let a strategy bypass global limits                    |
|Paper broker          |Simulate orders, partial fills, fees, and settlement                                  |Label synthetic or optimistic fills as observed reality|
|Exchange adapter      |In later phases, send demo/live orders and reconcile state                            |Blindly retry an ambiguous write                       |
|Reporting             |Show health, decisions, forecasts, costs, P&L, and unresolved discrepancies           |Hide rejects, losses, or unavailable data              |

The initial interface can be a CLI and a small local status page. Defer React, a separate Python service, Redis, Kubernetes, event buses, and custom MCP hosting until a concrete requirement justifies them.

### 3.2 Research boundary

The worker writes a sanitized research packet to an outbox. Claude reads that packet and returns a research document. A deterministic importer validates it before storing it. Research records are suggestions and evidence, not orders.

During paper development, these components can share a development machine. Before live operation, enforce real privilege separation:

- The researcher/developer identity cannot read production Kalshi secrets, change approved risk settings, modify the deployed executor, access its administration channel, or write directly to its database.
- The executor runs as a separate OS identity, container with enforced isolation, or separate host. A different folder or a prompt instruction is insufficient.
- Promote reviewed compiled artifacts and immutable strategy/configuration versions. Do not run production directly from a source checkout Claude can edit.
- Expose a narrow file or authenticated message interface for research input. Validate size, schema, IDs, paths, timestamps, and source references. No arbitrary deserialization or command execution.
- The execution identity does not have access to the Claude subscription credentials.

The exact deployment mechanism can remain simple. The requirement is enforceable separation, not a particular hosting vendor.

### 3.3 What happens when Claude is unavailable

Define dependency behavior per strategy:

1. An independently approved deterministic strategy may continue only while its market data, model inputs, account state, and other prerequisites remain healthy.
2. Any workflow needing a fresh reviewed research artifact stops new entries when that artifact expires or is missing.
3. Position reconciliation, cancellation attempts, risk monitoring, and settlement processing continue without Claude.
4. Quota exhaustion pauses research. It neither retries aggressively nor switches providers.

## 4. Subscription-only Claude integration

### 4.1 Implementation sequence

Start with manually initiated Claude Code research on exported packets. This proves the schema and review workflow without making a scheduler part of the first milestone.

Next, implement an optional bounded launcher using the documented official CLI. It can use a native OS scheduler or be invoked by a small research coordinator. Official Claude cloud scheduled tasks are an alternative later, once artifact transport and account availability are verified. They do not replace the continuous execution service.

### 4.2 Authentication and spending controls

Before every automated research run:

1. Run the documented authentication-status command in the exact working directory, configuration environment, and OS identity that will execute the research.
2. Require the expected subscription authentication method; initial implementation accepts the verified claude.ai route. Unknown or changed output fails closed.
3. Use an isolated configuration with no alternate model-provider keys, bearer-token routes, API-key helpers, Console profiles, federation credentials, or gateway configurations. Check effective settings without printing secret values.
4. Verify that the owner has disabled usage credits/extra usage. Authentication status alone does not prove this setting. If the installed product offers no reliable programmatic check, record an explicit owner-confirmed setup check, surface its date, and do not claim continuous machine verification. Keep unattended research off until this check is complete.
5. Reject the current API-only --bare behavior. Reevaluate supported flags after CLI upgrades; do not downgrade or patch the client to bypass changed access rules.
6. Do not enable spending, claim credits, add payment details, or change account billing settings automatically.
7. On any ambiguity, stop the research job, preserve its status, and continue useful non-AI development or monitoring.

Account-level settings can change outside the application. The status report must distinguish verified configuration, operator-attested billing settings, and unknowns. Do not advertise a mathematically guaranteed zero-dollar bill solely because an environment variable is absent.

### 4.3 Resource bounds

Proposed initial research configuration, adjustable without changing trading rules:

- Automatic scheduling off until setup verification passes.
- One research process at a time.
- At most two scheduled batches per day initially, five candidates per batch, and a bounded input packet.
- A documented maximum turn count and process timeout; initial targets are five minutes per batch and a small tool-call allowance, tuned during paper operation.
- Cache by packet hash, evidence revision, strategy version, prompt version, and recorded model identifier.
- Skip unchanged packets. On quota exhaustion, respect the product’s reset information when available; otherwise suspend and request a later owner-triggered attempt.
- Do not resume a growing conversation indefinitely. Each batch receives its own bounded context.
- Treat estimates of token use as telemetry, not an enforced subscription-dollar cap.

These limits are project budgets, not statements about Anthropic’s actual plan allowances. Research shares capacity with Andrew’s other Claude work.

### 4.4 Tool access and untrusted evidence

Run the launcher only in a clean, reviewed research workspace. Non-interactive Claude Code can discover hooks and MCP configuration; a freshly downloaded repository is not automatically safe to execute. [S2]

Allow only the specific read/search capabilities required. Prefer data collection in ordinary application code and give Claude the resulting packet. If optional MCP is used, expose only approved research tools. Do not attach a trade-capable community MCP and assume a confirmation argument prevents execution.

Treat market descriptions, webpages, repository instructions, and model output as untrusted data. They cannot grant privileges, change allowed domains, request secrets, rewrite live configuration, or authorize trading. Do not use unrestricted permission bypass flags to make scheduling easier.

### 4.5 Research output contract

Create schemas/research-record.schema.json with additionalProperties: false, explicit size limits, and versioning. Require these concepts:

|Field                                                  |Meaning                                                                                 |
|-------------------------------------------------------|----------------------------------------------------------------------------------------|
|`schemaVersion`, `researchId`, `packetId`, `packetHash`|Identity and exact input linkage                                                        |
|`createdAtUtc`, `validUntilUtc`                        |Research lifetime                                                                       |
|`marketTicker`, `eventTicker`, `seriesTicker`          |Exact known identifiers from the packet                                                 |
|`marketRulesHash`                                      |The reviewed rule revision                                                              |
|`disposition`                                          |`needs_review`, `insufficient_evidence`, or `no_issue_found`; none authorizes a trade   |
|`evidence[]`                                           |Source ID/URL, publication time if known, retrieval time, data hash, and claim supported|
|`uncertainties[]`, `invalidationConditions[]`          |Reasons evidence may be unusable or cease to apply                                      |
|`hypothesis`, `suggestedModelChange`                   |Research text for later review                                                          |
|`experimentalProbabilityYes`                           |Optional probability for paper scoring only, with method label and uncertainty; nullable|
|`researcherVersion`                                    |CLI, model, prompt, and tool/configuration versions available from the run              |

The importer rejects action commands, live flags, order size fields, risk-limit overrides, unknown tickers, duplicate IDs, impossible dates, expired records, missing required evidence, and malformed numbers. An experimental probability is stored in a separate research table that the live strategy evaluator cannot use as its authoritative probability input.

An evidence URL is not proof of truth. Validate authoritative numerical inputs independently through the corresponding collector. LLM-only extracted values remain research-only until independently checked.

## 5. Strategy and market scope

### 5.1 Initial universe

Initially permit only plain, fully collateralized, understood binary event contracts with the expected settlement rules. Exclude perps, leverage, unfamiliar collateral behavior, scalar payouts, multi-leg execution, and contracts whose resolution source is unclear.

Start with one small series allowlist and one horizon. Claude should recommend the first paper category after checking data availability. If historical forecast vintages or settlement definitions are unavailable, select a different testable category or collect prospective data; do not fabricate a backtest.

### 5.2 Candidate research directions

|Direction            |Why consider it                                     |What must be demonstrated                                                                                                       |
|---------------------|----------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------|
|Weather thresholds   |Repeated outcomes and measurable forecast inputs    |Exact station, local date, observation convention, threshold/rounding rules, forecast vintage, and calibrated error distribution|
|Economic releases    |Defined release events and known publication times  |Point-in-time forecasts, revision handling, release-specific data, and enough independent releases                              |
|Related-market checks|Logical relationships can reveal inconsistent prices|Equivalent rules and timing, complete outcome sets where needed, executable depth, costs, and feasible execution                |

Weather is not automatically easy or profitable. A point forecast is not a probability distribution. Related-market anomalies are not risk-free arbitrage when orders cannot fill together. Defer trading multi-leg structures in the first implementation.

### 5.3 Strategy definition

Each strategy version must identify:

- Allowed series, market types, horizon, and data prerequisites.
- Model code/version, training window, input fields, feature timestamps, and calibration method.
- Probability method and whether uncertainty is statistically estimated or a conservative policy buffer.
- Entry condition, acquisition limit price, fee model, maximum holding time, settlement/exit policy, and abstention conditions.
- Event and correlation grouping, risk allocation, and validation protocol.
- Research artifact dependencies, if any, and expiry behavior.
- Approval status and exact model/configuration hashes.

Unknown correlation grouping is not a reason to assume independence. Use a conservative shared bucket or reject the market.

### 5.4 Expected value and executable prices

For an ordinary binary YES contract paying $1 if the event occurs, held through settlement:

```
estimatedNetProfit = quantity * (conservativeProbabilityYes - executableAverageAcquisitionPrice) - estimatedFees - otherIncrementalCosts
```

For NO, use the matching NO probability and NO acquisition cost. This is a calculation conditional on the forecast being useful; it does not validate that forecast.

Use executable book depth for the intended quantity, never last trade as a guaranteed fill. Keep average price, limit price, spread, and incremental slippage separate to avoid double-counting. Apply the current applicable fee schedule, rounding, and effective dates; unknown fees reject a trade.

Use C# decimal for money, quantities, and exchange price conversion. Statistical model internals may use floating point with explicit conversion validation at the boundary. Respect each market’s tick/price grid. First live version can restrict to whole contracts while correctly reading fixed-point exchange fields.

Do not choose eight percentage points because an earlier answer suggested it. Predeclare model-specific thresholds before evaluating held-out results. Do not call a hand-selected probability haircut a confidence interval.

## 6. Risk accounting and operator control

### 6.1 Required separate quantities

Track account cash, experiment allocation, filled exposure, pending-order reservations, unsettled worst-case loss, realized/unrealized P&L, fees, and operating expenses separately.

At minimum, configure these limits before any live activation:

- Maximum acquisition loss per order and per market.
- Maximum loss per event and broader correlation group.
- Maximum total unsettled capital at risk, including all reservations.
- Maximum newly committed capital per day, if needed to bound repeated turnover.
- Daily loss trigger and cumulative drawdown trigger.
- Maximum open orders, entry decisions per day, and maximum order lifetime.
- Minimum available cash buffer and approved experiment allocation.

For simple purchased binary positions, use acquisition cost plus applicable fees as the conservative amount at risk. Reserve unfilled orders at their worst allowed fill cost plus fee allowance. Account for both pending and confirmed exposure; do not grant netting credit without a separately verified settlement/collateral model.

Persist reservations in the same database transaction that records an order intent. Concurrent candidates cannot independently spend the same remaining capacity. A canceled request only releases capacity after the exchange outcome is confirmed. An unknown submission retains its reservation.

Existing manual positions and orders in the same account affect account risk. Reconcile them or use a verified isolated allocation mechanism. Do not assume every account has a suitable subaccount capability. If unexplained external activity invalidates risk accounting, stop new entries.

### 6.3 Daily loss and drawdown semantics

Use America/Chicago for the reporting day, with UTC storage and correct daylight-saving boundaries. Persist the day’s opening equity and distinguish deposits/withdrawals from performance.

For marked equity, use a documented conservative executable-liquidation valuation where feasible. Daily cash-flow-adjusted P&L is:

```
currentEquity - openingEquity - depositsDuringDay + withdrawalsDuringDay
```

Show realized P&L separately. If required marks are unavailable or stale, label valuation uncertain and block new risk. Do not substitute a favorable midpoint or silently retain a stale high valuation.

Define cumulative drawdown from a persisted cash-flow-adjusted equity high-water mark beginning when the approved allocation is activated. Let adjusted equity equal current equity minus cumulative net external cash flows since activation; the high-water mark is the maximum adjusted equity observed. Dollar drawdown is that peak minus current adjusted equity. Deposits, withdrawals, restart, midnight, and a new strategy version must not silently reset the baseline. Any intentional baseline reset is a separate logged operator action.

A daily loss trigger is a stop-opening-risk control, not a guaranteed maximum loss. Positions can lose more after it triggers, and cancellation requests can race with fills. An exact prospective loss budget would require tighter control of worst-case remaining exposure.

When a daily or cumulative trigger fires:

1. Persist the halted state before any further submission.
2. Block new risk and attempt to cancel outstanding entry orders.
3. Keep exposure reserved until cancellation or fills are confirmed.
4. Continue reconciliation, position monitoring, and settlement.
5. Follow a previously approved position-management policy; do not automatically dump positions with unrestricted orders.
6. Require an explicit operator reset. Restarting the process or crossing midnight does not clear a safety halt.

The operator can always pause new entries. A manual pause must work independently of Claude. No automatic deposits, withdrawals, reallocation, limit increases, or model promotion are in scope.

## 7. Exchange lifecycle and current API compatibility

### 7.1 Adapter responsibilities

Keep domain concepts such as BuyYes and BuyNo separate from exchange wire fields. For each supported operation, test conversion to the current single-book API, including complement-price direction and risk cost. A passing serialization test is insufficient if the economic side is reversed.

Before demo integration, retrieve the current official contract for market data, orders, balances, fills, positions, settlements, authentication, precision, fees, pagination, rate limits, and exchange health. Pin a reference snapshot or content hashes. Do not assume old repository examples remain valid.

Restrict the initial execution design to limit-priced entries. The strategy must explicitly choose time-in-force. A marketable limit can execute immediately but still caps price; a passive limit has uncertain execution. Neither is a guaranteed fill.

Use separate demo and production credentials and explicit endpoint allowlists. Credentials are configured privately by the operator in the executor environment, never pasted into Claude, a research packet, source control, logs, or this specification.

### 7.2 Durable lifecycle

Represent the lifecycle with durable states such as:

- CandidateRejected
- IntentReserved
- Submitting
- SubmissionUnknown
- Accepted
- PartiallyFilled
- Filled
- CancelPending
- Canceled
- Expired
- Rejected
- Reconciled

Use the actual exchange status as evidence; do not force these labels into an inaccurate one-to-one mapping with wire values.

Persist a unique local intent and reservation before sending an order. Record the request fingerprint, strategy version, signal ID, client order ID, and risk decision. Keep historical uniqueness locally even after an exchange order terminates.

Deduplicate the economic signal separately from the network request. The strategy defines a stable key over its version, market, side, and decision/evidence window. Repeated scans and restarts must recover that key instead of generating a fresh UUID that authorizes another entry. Additional entries or re-entry require an explicit approved strategy rule.

Immediately before dispatch, the executor’s serialized submission gate rechecks the persisted halt state, approved strategy/configuration hashes, account reconciliation, quote/evidence freshness, and that the exact request still fits its reservation. A halt or expiry after initial reservation blocks dispatch. A request already sent cannot be recalled by this check and remains subject to cancellation/reconciliation.

After a timeout, lost connection, or ambiguous server response, mark SubmissionUnknown and reconcile. Do not create a new order ID and submit again to make the error disappear. Do not treat one empty or delayed read as proof that the first request was rejected. Kalshi’s documented open-order duplicate check is not a permanent exactly-once guarantee. [S9]

On startup, reconcile prior intents, open orders, fills, and positions before permitting new entries. Use private stream updates where appropriate plus periodic REST reconciliation; design for delayed, duplicate, missed, and out-of-order events. Persist all material state transitions. Unknown exposure remains reserved.

Partial fills reduce the unfilled reservation while increasing filled exposure. Cancellation does not reverse previous fills. A successful submission response is parsed for actual filled and remaining quantities; success status alone does not imply a resting order. [S8]

### 7.3 Operational failure rules

New risk is blocked on stale order books, stale required model inputs, invalid clocks, changed rules, unknown fees, unreconciled account state, persistent exchange errors, or a safety halt.

Back off on rate limits and enforce bounded retries for read operations. Write retries follow lifecycle-specific reconciliation rules. Respect exchange limits; do not evade them with multiple accounts or keys.

Keep a recoverable database backup and a restart procedure. An append-only audit log with hashes helps detect changes but is not fully immutable against a machine administrator. Describe its actual guarantees accurately.

## 8. Honest validation and promotion

### 8.1 Distinguish three environments

1. Fixture replay: Synthetic or frozen inputs establish deterministic behavior and failure handling. Fixture profitability is meaningless.
2. Production-data paper evaluation: Contemporary real observations support forecast scoring and conservative simulated economics. These are simulated fills, not realized live returns.
3. Kalshi demo: Mock funds test authentication, order behavior, and reconciliation. Demo results do not establish an economic edge on production markets. Consult current demo documentation. [S16]

Keep their databases or dataset namespaces separate. Never blend fixture, demo, paper, and live P&L into one reported track record.

### 8.2 Evidence protocol

Before evaluating a strategy, freeze its feature definitions, parameter search procedure, validation windows, execution assumptions, metrics, and promotion criteria. Record every tested variant and rejected hypothesis. A changed strategy begins a new version; do not relabel prior test results as its out-of-sample evidence.

Store publication, retrieval, observation, and decision times independently. Keep source vintages and later revisions distinct. Archive decision-time inputs, market rules, quote depth, and fees so another run can reproduce the calculation.

Use walk-forward or equivalent time-ordered holdouts. Check selection, survivorship, and look-ahead bias. Do not reconstruct forecast inputs with today’s revised values. If historical depth or queue data is missing, state the limitation and collect prospective observations rather than inventing fills.

Related contracts from one event are not independent observations. Estimate uncertainty at the appropriate event/date grouping and disclose concentration. A large number of contracts is not automatically a large sample of independent forecasts.

### 8.3 Metrics

Report:

- Forecast coverage, abstentions, and reasons for rejected candidates.
- Calibration and Brier score, with an appropriate same-time market baseline; report probability comparisons separately from executable trading costs.
- Sample size in both contracts and independent event groups.
- Net simulated P&L after estimated fees and execution assumptions; live realized P&L only when live trades actually exist.
- Turnover, exposure duration, fill rate, partial fills, spread and depth, drawdown, and performance by market family.
- Sensitivity to fees, less favorable fills, forecast errors, and model drift.
- Confidence/uncertainty estimates whose assumptions are disclosed.
- Incremental infrastructure/data/model charges and an optional allocation of existing subscription cost. Show both incremental cash economics and fully allocated economics.

Win rate alone does not demonstrate edge. Forecast accuracy alone does not demonstrate profitable execution. Correct risk controls do not establish either.

### 8.4 Paper execution assumptions

Start with a conservative, documented executable-depth model for marketable limits. Apply latency and quantity constraints, and do not reuse the same recorded liquidity to fill an unlimited sequence of paper orders.

A simulated order can use only suitable observations at or after its simulated arrival. Do not reuse the pre-decision quote and merely add latency to the reported fill timestamp. If the price or quantity disappears before arrival, the simulator must reflect that change. Missing post-arrival evidence produces an uncertain/no-fill result under the declared conservative model.

Do not fill a passive order merely because the quote touched its limit. Either collect sufficient information for a defensible queue/fill model or show explicit conservative fill scenarios, including no fill. Reconcile eventual outcomes against the actual resolution source.

### 8.5 Promotion outcomes

Use three outcomes: pass, fail, and insufficient_evidence.

There is no automatic pass after two weeks, 100 trades, or one profitable backtest. Predeclare the required precision/evidence and cost sensitivity for the chosen strategy before the held-out evaluation. Show whether plausible alternative assumptions erase the apparent advantage.

Live promotion requires all of the following:

- Integration and failure-handling acceptance tests pass.
- A reviewed strategy version has evidence appropriate to its hypothesis and a clearly stated uncertainty assessment.
- Execution assumptions and operating costs do not explain away the apparent edge.
- Actual user-selected capital/risk settings and deployment isolation are complete.
- An operator authorizes that specific version and allocation.

If evidence is insufficient, keep collecting or stop the experiment. A faithful abstention or failed hypothesis is a valid result.

Select a narrow, data-supported hypothesis. Build or reuse a transparent forecasting method, freeze the evaluation protocol, and collect enough independent outcomes to assess it. Make an explicit decision to continue, revise, or stop.

Acceptance: Reproducible results with costs, baselines, uncertainty, and rejection reasons. It is acceptable to conclude that no edge has been demonstrated. Observation time is distinct from coding time and cannot be compressed by an agent.

Implement the current official order contract against the demo environment with separate credentials supplied privately by the operator. Verify real lifecycle behavior, reconciliation, persistence, precision, timeouts, and risk controls.

Prepare, but do not automatically activate, a reviewable release containing strategy/model/configuration hashes, validation report, actual limits, isolated deployment, monitoring, and recovery procedures. The owner decides whether evidence warrants any live pilot.

Acceptance: Explicit authorization for that release and allocation. Live changes are not implied by approving this specification or by passing demo tests.

### Phase 6 — Optional improvements

Add richer dashboards, cloud research scheduling, additional strategies, or an always-on host only when they solve a demonstrated operational need. Preserve the subscription-only billing constraint.
